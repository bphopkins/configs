# Neovim configuration audit — second pass (2026-08-22)

Dated record, true as of 2026-08-22; moved verbatim from the root `CLAUDE.md`
on 2026-08-26 (context-policy Stage 2). A full-config audit on `bigfed` after
the latency work (`insert-latency-2026-08.md`), covering the LazyVim layer the
first pass never reached. Verdicts recorded so they are not re-derived; the
operative one-liners distilled from them live in `nvim/CLAUDE.md`.

- **The LazyVim UI layer is not a latency lever — measured.** Ablating `statuscolumn`, `relativenumber`, `cursorline`, snacks indent guides and `g:snacks_animate` one at a time (and all at once) moved typing p50 at the end of the fixture's 2080-char line by under 1 ms (32.5 ms baseline on bigfed). Scroll-settle probes were too noisy to attribute anything (132–179 ms across runs), and snacks' scroll *animation* never measurably engaged in the embedded-UI harness — so its interactive feel is untested rather than cleared. If scrolling on `fedxps` ever feels heavy, toggle live with `:lua vim.g.snacks_animate = false` and judge by feel; that global is LazyVim's own documented switch. `clipboard=unnamedplus` costs ~6 ms per normal-mode `x`/`yy` here (a wl-copy spawn per delete/yank) — left alone; re-measure on fedxps before drawing any conclusion there. Startup is healthy (38 ms lazy startuptime, 19 of 38 plugins loading at startup).
- **The markdown `<CR>` checkbox mapping does not fight blink's enter-accept** — verified live, not assumed. blink applies its own buffer-local `<CR>` over ours and snapshots ours as its *fallback*, so Enter accepts a selected completion while plain Enter still continues checkbox lists. Not a conflict; don't "fix" it — but it rests on undocumented blink behaviour, so both halves are pinned by four checks in the latency suite (same day).
- **The prose-gate's look-behind was too narrow — a real bug the suite passed over.** `in_latex_context()` read a 60-char window, so `\cite{` fell out of it once a key list or prenote ran past ~60 chars, and both completion sources went dead *mid-argument* — precisely where completion earns its keep in citation-heavy chapters. Found by direct probe the same day (the suite's arguments were all short — a check that cannot fail is worse than no check, again). Window widened to 300: the scan costs microseconds; it was the *sources* that were expensive, never the gate. Two long-argument checks added.
- **Auto-save failures are loud now, once per failure episode** — see the auto-save section of `nvim/CLAUDE.md`, including the `'confirm'`-dialog trap the fix itself uncovered.
- **Notification bubbles made readable** (`snacks.lua`, user request): the chain is `vim.notify` → noice → snacks.notifier (noice adds no sizing or timing — verified by probe), and snacks' stock values were the whole symptom: 3 s timeout, width capped at 0.4 of columns, `wrap=false` clipping long lines at the bubble edge. Now 10 s / 0.55 / wrapped; `dim()` in snacks treats values ≤ 1 as editor fractions and only *clamps* the content-sized bubble, so short notifications render as before. Auto-dismissal deliberately kept; `<leader>n` holds full history regardless. All three styles were compared live, side by side, with manual dismissal (`<leader>un`) exercised: **compact kept** — fancy's timestamp header costs two rows per bubble, minimal drops titles entirely.
- **bib/bibtex no longer list the vimtex completion source.** cmp-vimtex completes citations, labels and commands *for tex buffers* and has nothing to offer while authoring entries — and in a bib-only session the plugin (ft-gated to tex) was never even loaded, leaving the provider half-wired. Snippets (the `latex-workshop` entry templates) and path remain, and `in_latex_context()` doesn't gate non-tex filetypes, so entry templates stay available everywhere in a bib file.
- **Considered and declined: confining the vimtex source to brace contexts** (so bare-`\` completion would be snippets-only). Measured state: typing `\ne` yields 119 snippet items + 81 package-harvested commands, but the harvest ranks below the snippets and mostly lives beyond the ten visible rows, so the decluttering is below the fold — while the harvest is how a half-remembered, uncurated command (`\nsubseteq`, biblatex variants) gets found at all, and the change would grow custom gating on the most upstream-fragile chain (blink.compat → cmp-vimtex). Revisit only on felt annoyance; the better remedy for a repeatedly-accepted harvest item is curating it into a snippet (a third library file in `lua/snippets/` + one name in `snippets.lua`'s `filetype_extend`).
- **Trimmed the two never-loaded plugins** (`enabled = false`; 38 → 36): friendly-snippets in `completions.lua` (a blink.cmp dependency, but with `snippets.preset = "luasnip"` and no vscode loader anywhere, nothing ever reads it — the 1063 tex snippets are entirely the two generated libraries) and catppuccin in `colorscheme.lua` (LazyVim's alternative scheme, never activated; every LazyVim reference to it is `optional = true`). The `name = "catppuccin"` on the disable fragment is load-bearing — without it lazy.nvim files the fragment under a new plugin named "nvim" and disables nothing. Reverting either is deleting its line.
- **`vimtex.lua` lost its inert `ft` key**: an explicit `lazy = false` wins over any load trigger, so the `ft` list only misled readers into thinking the plugin was filetype-gated. Eager loading is VimTeX's own recommendation.
- **The plugin lockfile is tracked on purpose, and the sync now says what to do with it.** `lazy-lock.json` travels through git but applies itself nowhere, so the machines silently ran different plugin versions between ad-hoc updates. Decision: keep the lock tracked — it is the rollback record (`git log nvim/lazy-lock.json` + `:Lazy restore` is the one-move return to last-known-good after an upstream break) and the only convergence target restore can aim at; keep the background checker (advisory only, never causes skew); keep updates ad hoc on either machine. The missing piece was the pull side, closed in `_gsync_pull_hints`: a `configs` pull that changes `nvim/lazy-lock.json` prints `run: nvim --headless "+Lazy! restore" +qa`, exactly like the re-source and restow hints (and unlike those it fires on plain modifications, because a pulled lock changes nothing until nvim re-pins to it). If both machines update the same plugin between syncs the lock can conflict during `gpushall`'s rebase; the auto-abort already names the repo — resolve by taking either side, restore, and run the two nvim suites if VimTeX or blink moved. Considered and **declined**: untracking the lock (loses rollback, reproducibility, and the convergence target, buying only the absence of rare conflicts) and auto-running restore inside the pull (seconds of headless nvim and plugin checkouts inside the most safety-critical path, against the hints-not-actions posture).
